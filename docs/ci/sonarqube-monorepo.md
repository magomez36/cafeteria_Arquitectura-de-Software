# SonarQube Cloud in the pnpm monorepo

## Repository configuration

The CI workflow runs `pnpm coverage`, reads the per-workspace LCOV files from `sonar-project.properties`, and runs the pinned official SonarSource scan action with `sonar.qualitygate.wait=true`. Missing project identity or token fails the `quality` job; a missing or `not-computed` gate is never converted into success. Documentation-only changes do not run Sonar because there is no executable source change.

Before enabling the PR check, a repository administrator must:

1. Import `magomez36/cafeteria_Arquitectura-de-Software` into the approved SonarQube Cloud organization and bind it to GitHub. Use the project key and organization key generated by Sonar; do not guess them.
2. Add GitHub Actions repository variables `SONAR_PROJECT_KEY` and `SONAR_ORGANIZATION` with those exact values.
3. Create a Sonar analysis token restricted to this project and add it as the Actions secret `SONAR_TOKEN`. Never commit or paste its value into files or PR comments.
4. Set `main` as the new-code reference branch and select a quality gate that applies to new code and enforces all constitutional conditions below.
5. Confirm the GitHub App integration publishes the Quality Gate result to the real PR and that a failed gate causes the `quality` check to fail.

## Required new-code conditions

- Coverage at least 80% for new code; at least 95% for new code in `promotions`, `orders`, and `payments` when those modules are introduced.
- Zero new bugs and zero new vulnerabilities.
- All new security hotspots reviewed.
- New-code duplication below 3%.
- A ratings for maintainability, reliability, and security.

SonarQube Cloud's built-in Sonar way gate covers 80% new-code coverage, A ratings/no new bugs or vulnerabilities, all new security hotspots reviewed, and duplication up to 3%. The strict project requirement is duplication **below** 3%; the administrator must ensure the configured condition enforces that strict bound. Module-specific 95% coverage must be checked by the gate or a separate required CI check when the module source exists; a global 80% condition does not satisfy it.

## Coverage reports

Run `pnpm coverage` from the repository root. Expected LCOV files:

- `apps/api/coverage/lcov.info`
- `apps/web/coverage/lcov.info`
- `apps/worker/coverage/lcov.info`
- `packages/contracts/coverage/lcov.info`
- `packages/feature-flags/coverage/lcov.info`
- `packages/ui/coverage/lcov.info`

The test suite for CI policy remains `pnpm test:ci`; it is not part of the application source scope in `sonar-project.properties`.

## Monorepo PR acceptance experiment

The scan is intentionally blocking for code changes. Once credentials and project binding exist:

1. Run a normal PR and inspect the Sonar analysis SHA, all six LCOV imports, new-code metrics, and `quality` conclusion.
2. On a disposable branch, add a temporary production-source fixture whose coverage is below 80%; verify the Sonar Quality Gate and the GitHub `quality` check fail. Remove the fixture in a separate cleanup change.
3. Verify the GitHub branch rule requires the stable `quality` check, and that a `failed`, `not-computed`, missing-token, or missing-project result cannot merge.
4. Keep this task incomplete until the experiment has run on the actual PR and the result is visible in GitHub Actions/SonarQube Cloud.

If the native monorepo analysis does not publish a blocking check, do not weaken the gate. Follow the alternate project/aggregator investigation in `research.md` and document the observed result before changing the integration design.
